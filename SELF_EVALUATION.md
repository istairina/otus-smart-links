### 2. Расширение функционала без изменения кода (макс 3 балла)

#### 2.1. Реализовано не менее 2 единиц требований (1 балл)

#### 2.2. Middleware или аналог (1 балл) +
- `contextMiddleware` - извлекает контекст из запроса:
  - Автоматически обрабатывает все поля из типа `Context` (time, userAgent, language)
  - Принимает все заголовки, но формирует контекст только с определенными полями
  - Поддерживает конфигурацию для полей с особой логикой обработки
  - Для добавления нового поля достаточно обновить тип `Context` и шаблон
- `ruleEngineMiddleware` - вызывает rules-service для оценки правил:
  - Отправляет контекст в rules-service через POST /evaluate
- `redirectMiddleware` - выполняет редирект на основе результата:
  - Защита от бесконечного редиректа (проверка на тот же хост)
  - Возвращает 400 при обнаружении цикла редиректа

#### 2.3. Динамические плагины или DSL (1 балл) +

**Плагинная архитектура условий:**
- `ConditionPlugin` интерфейс
- `AbstractCondition` базовый класс
- Автоматическое обнаружение плагинов через `initializeConditions()`
- Динамическая регистрация в `RuleEngine` через Map
- Правила описываются в JSON (DSL):
  ```json
  {
    "id": 1,
    "conditions": [
      { "type": "time", "start": "22:00", "end": "23:00" },
      { "type": "user-agent", "include": "Chrome" },
      { "type": "language", "is": "ru" }
    ],
    "action": { "redirectTo": "https://yandex.ru" }
  }
  ```
- Поддержка двух типов проверки:
  - `is` - точное соответствие
  - `include` - частичное соответствие (проверка на вхождение подстроки)
- Реализованные условия:
  - `time` - проверка времени в диапазоне (start, end)
  - `user-agent` - проверка User-Agent (is, include)
  - `language` - проверка языка из Accept-Language (is, include)

### 6. Описаны проблемы сложности и способы их решения (1 балл) +

#### 1. Проблема порядка запуска и зависимости между сервисами

**Проблема:** При параллельном запуске сервисов `rules-service` пытается загрузить правила из `db` до того, как `db` готов к обработке запросов. Это приводит к ошибкам подключения и падению сервиса.

**Решение:**
- Реализована логика повторных попыток (retry) с экспоненциальной задержкой
- Сервер `rules-service` запускается немедленно, загрузка правил происходит асинхронно в фоне
- Если загрузка не удалась, сервис продолжает работать без правил 
- Правила можно загрузить позже через эндпоинт `POST /reload`

---

#### 2. Проблема недоступности зависимых сервисов во время работы

**Проблема:** Если `rules-service` недоступен, `redirect-service` не может обработать запросы пользователей, что приводит к ошибкам 500 и плохому пользовательскому опыту.

**Решение:**
- Реализована обработка ошибок с graceful degradation
- При недоступности `rules-service` устанавливается `ruleResult = null`
- Запрос продолжает обрабатываться, возвращается 404 (правило не найдено)
- Ошибки логируются, но не прерывают обработку запроса

---

#### 3. Проблема расширяемости: добавление новых типов условий

**Проблема:** При добавлении нового типа условия (например, проверка устройства, языка и т.д.) требуется изменять код в нескольких местах, что нарушает принцип открытости/закрытости (Open/Closed Principle).

**Решение:**
- Реализована плагинная архитектура на основе паттерна Strategy
- Базовый класс `AbstractCondition` определяет контракт
- Новые условия наследуются от `AbstractCondition` и автоматически обнаруживаются
- `RuleEngine` использует Map для динамической регистрации плагинов

---

#### 4. Проблема синхронизации правил между сервисами

**Проблема:** При изменении правил в `db` сервисе, `rules-service` продолжает использовать устаревшие правила в памяти, что приводит к неконсистентности данных.

**Решение:**
- Реализован эндпоинт `POST /reload` для принудительной перезагрузки правил
- Правила загружаются при старте сервиса
- Возможность обновления правил без перезапуска сервиса

---

#### 5. Проблема масштабирования и производительности

**Проблема:** При росте нагрузки монолитное приложение становится узким местом. Все запросы обрабатываются одним процессом, что ограничивает пропускную способность.

**Решение:**
- Микросервисная архитектура позволяет масштабировать каждый сервис независимо
- `redirect-service` может масштабироваться горизонтально (несколько инстансов)
- `rules-service` может кэшировать правила и обрабатывать запросы параллельно
- `db` сервис можно заменить на реальную БД (PostgreSQL, MongoDB) без изменения других сервисов

---

#### 6. Проблема бесконечного редиректа

**Проблема:** Если правило делает редирект на тот же хост (например, `localhost`), браузер интерпретирует это как относительный URL и делает запрос на тот же сервис, что приводит к бесконечному циклу редиректов.

**Решение:**
- Реализована проверка `isSameHost()` в `redirectMiddleware`
- При обнаружении редиректа на тот же хост возвращается ошибка 400 вместо выполнения редиректа
- Рекомендуется использовать полные URL с протоколом (https://example.com) в правилах
